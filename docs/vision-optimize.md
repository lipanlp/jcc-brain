#### 156.3ms → 190.5ms 的原因

- T1 前后 `src/jccbrain/vision/` 的 Git tree 完全相同：`4f6d153` 与 `d186857` 均为
  `33585def97e33cc54e35c7dc47729e67efeb165b`。T1 只调整构建资源，没有改模型、识别算法或输入。
- 总耗时增加 **34.2ms**，其中 OCR 从 **135.6 → 168.0ms**，增加 **32.4ms（占增量 94.7%）**；
  单位 **18.9 → 20.5ms**。OCR 格数均为 **9.67/帧**，逐字段评分完全相同，识别工作量未增加。
- 主目录另一个 `jccbrain gui` 进程在 02:08 启动，落在 T1 前评测（02:06）和后评测（02:09）之间；
  T2 调查时观察到主目录 GUI 占约 **52%–70% CPU**，同时游戏和 WindowServer 持续占用资源。
  T2 开工基线为 **197.9ms**；该 GUI 自行退出后，原版源码恢复到 **160.7ms**，接近 T1 的 156.3ms。
  用户已允许临时暂停该 GUI，但执行隔离评测时进程已退出，没有暂停、终止或遗留待恢复的进程。
- 因此，回退主要发生在 OCR 模型执行阶段，证据支持**外部资源争用**，主目录的第二套视觉 GUI 是已发现的
  干扰源。T1 当时没有逐进程 CPU 采样，不能将全部 34.2ms 精确分摊给某个进程。之后无 GUI 的原版评测也会
  随系统负载波动至 185.5ms；这说明单次耗时不能作为打包导致算法变慢的证据。

历史结果保存在 `/tmp/jcc-vision-t1-before.json`、`/tmp/jcc-vision-t1-after.json`；
T2 开工为 `/tmp/before.json`；GUI 退出后的原版与初始并行方案对照为 `/tmp/jcc-vision-t2-isolation.json`。
初始方案将整个 `read_cells` 搬到线程池，原版 **160.7ms**、该方案 **177.4ms**，因此改为下面的分阶段实现。

#### 最终实现与验证口径

1. `GameReader` 在调用线程完成裁剪、数字模板和缓存判断，然后发出数字/文字两个 OCR 模型批次；
   模型运行期间完成血条、星级、颜色直方图和必要的 Vision 特征。得到完整 OCR 的 phase / 商店名字后，
   再更新跟踪、分组、图库和自动标注。相位提示只影响特征是否提前计算，最终相位解析沿用原逻辑。
2. 血条绿色像素一次分段，保留原有间隙、长度、边框和跨行连接规则；47 张标准/track 截图的血条坐标与原版一致。
   预计算特征无结果时不会重复请求；OCR 后发生新对局重置而缺少特征时仍按原路径提取。
3. 商店名字、商店羁绊、左侧羁绊的同区域小格保留原黑边后成组检测；识别从原像素裁行。玩家栏、海克斯描述
   仍独立检测，避免拼图改变长文本。模型、输入分辨率、识别阈值与行缓存规则保持原值。
4. 实时/回放 provider 在 `start()` 中各预热 RapidOCR det/rec 一次；并发调用只发布一个已成功预热的 reader，
   失败可重试。合成预热图不进入文字缓存。任一单位、OCR 批次或格子检测失败，等待已发出的相关任务退出后再报错。
5. 评测新增 `--timing-only`（读取目录全部 jpg，track 同名图片不套用标准集参考答案），记录初始化、首帧和每轮均值。
   可显式用 `--warmup` 单列预热；**最终验收保持默认不预热，包含每轮冷首帧和全部帧**。
   `--repeat 3` 在同一进程内每轮新建 reader；首帧数据不代表三次新的冷进程启动。
   `total` 仍为 `GameReader.read` 内单帧墙钟耗时，图像加载和 reader 初始化另列；并行后的 OCR / units 有重叠，不能相加。

最终对照使用同一版评测脚本，原版视觉源码从 `d186857` 导出到临时目录，未切分支或修改主目录。
四次评测按标准集原版→新版、track 原版→新版顺序独立执行；游戏保持运行，无测试、打包或第二个评测同时争用 CPU。

## 做了什么

1. **数字模板匹配** `eye/digits.py`：亮度 Otsu（或近白色）二值化 → 连通域 → 横向重叠合并 → 按窗口高度比例
   过滤字高（0.8%~1.85%）→ 28×20 归一化相关。模板 `digits.npz`（3KB，每类若干写法）由
   `scripts/make_digit_templates.py` 从样本切出。regions.json 的 `"digits": true | "white"` 标记走模板的区域；
   新增 `trait_count` 区域（羁绊激活人数大数字，OCR 常漏）。
2. **OCR 后端可切换** `vision.ocr = rapid | vision`：
   - `eye/rapid.py`：RapidOCR(PP-OCRv4) 原尺寸检测（线程池，商店/羁绊小格按区域成组），逐行识别；行级缓存（像素完全一样 → 精确命中；
     不含数字的文字行按白色字形 XOR 容差命中，玩家列表背后龙纹在动也能命中）；「图标 + 1~3 位数字」的血量行
     直接模板读数；识别不出的行交给 Apple Vision 补认（「斗士」PP-OCR 读不出）。
   - Apple Vision：拼图按区域分组（拼图组成一变 Vision 会整行丢字，实测「狂战士」行）。
3. **词典**：`Dictionary.from_db` 带英雄羁绊、海克斯名；数据库羁绊名映射成游戏显示名（`TRAIT_DISPLAY`，
   目前只有「约德尔人 → 约德尔人和朋友」）。`dict.json` 改由 `scripts/make_vision_dict.py` 生成。
4. **商店**：认出英雄后羁绊直接用数据库；道具卡输出 `item: true`、费用读卡面数字；星形检测输出可升星 `upgrade`。
5. 人口水印 CLAHE 增强；玩家列表过滤矮行图标、「5100」→100。

## B2 截图保护（#C）

`WindowCapture` 为 CG / SC 各维护一个进程共享的 daemon 工作线程，每后端最多等 2 秒；

CG 连续失败两次切到 ScreenCaptureKit 单张截图，每 60 秒探测 CG，成功切回。
切换或探测时一次 `grab()` 最多包含 CG、SC 各一次等待；2 秒限制针对单个后端。
状态增加 `capture_backend`；SC 按 windowID 缓存窗口，按点尺寸配置，仍用 CoreGraphics 转 BGR。
